# Final Fusion · Build and test

The host is a native macOS app. The Mac viewer is built with the host; the Go helper also builds the Windows viewer. The host creates a paired viewer for each user's own setup. This repo has no preconfigured relay or personal receiver file.

1.0.20 uses a new relay protocol. Prepare the signed viewer update or a separate installation package before switching the relay. Approve each viewer again after the switch. Reinstall the boot helper after pairing if you use login-window access. A fixed signing identity is required for automatic Mac viewer updates.

## Build

On a Mac, install the Xcode Command Line Tools, a macOS SDK with ScreenCaptureKit, and Go as specified in `Link/go.mod`. Install the Windows resource tool with `go install github.com/tc-hib/go-winres@v0.3.3`. Then:

```sh
export GO_TOOL="$(command -v go)"
export WINRES_TOOL="$(go env GOPATH)/bin/go-winres"
out="$(mktemp -d)"
SIGN_IDENTITY=- bash build.sh "$out"
app="$out/파이널 퓨전.app"
bin="$app/Contents/MacOS/StudioRemote"
```

This is a local development build. It uses ad hoc Mac signing and an unsigned Windows viewer; it is not an Apple-notarized or Windows-signed distribution. A user-provided signing identity can be selected with `SIGN_IDENTITY`. See [Relay/SETUP.md](Relay/SETUP.md) for the user's own Cloudflare setup.

## Check

```sh
codesign --verify --strict --deep "$app"
lipo -archs "$bin"
"$bin" --self-test
"$bin" --test-loopback
"$bin" --test-video
"$bin" --test-native-video
"$bin" --test-session "$out/session.png"
"$bin" --test-separated-transport
mkdir -p "$out/fixture"
"$bin" --test-export "$out/fixture"
"$bin" --test-update-export "$out/fixture"
FINAL_FUSION_LANGUAGE=ko FINAL_FUSION_PREVIEW_MODE=agent "$bin" --preview-ui "$out/preview"
(cd Link && go test ./... && go test -race ./...)
```

The native video and session tests use generated data and a local connection. Preview states include `connecting`, `exporting`, and `updating` via `FINAL_FUSION_PREVIEW_STATE`. Use the viewer generated by `--test-export` to preview the Mac viewer. These checks do not substitute for checking real receiving laptops.

The session test checks automatic transfer to older Mac viewers, the 1.0.0 update request, and the version check after installation. Only the host's already approved Mac viewers receive an update; the viewer verifies the downloaded file and its bundled profile before installation. A certificate-signed viewer requires the same signing identity for the replacement. Windows viewers are exported again from the host. When the host is configured with a signing identity, a viewer signing failure stops the export so the host cannot send an update signed with a different identity.

The 1.0.3 session test also simulates a screen saver, a display mode still settling, and a suspended video stream. It checks that a fresh desktop frame starts the full-quality session and that a persistent screen saver leaves remote input available before reconnecting. This test uses simulated screen saver states.

To check 1.0.4 on hardware, disconnect the host monitor, reconnect from a Mac viewer using Full quality, and verify that the received dimensions match the viewer and fill the display. This exercises the virtual primary display path.

1.0.5 moves the link between the host app and its helper to a local socket that only the app's own macOS account can open. The loopback test checks the socket's permissions, that a wrong code is refused before capture, and that the socket is removed.

1.0.6 fixes unlocking a host whose display went to sleep while locked. The lock screen holds a password check until macOS reports an active user, and events posted by the app do not count while the display is off, so a correct password was rejected. The host now declares user activity when viewer input arrives, at most once a second. To check it on hardware, let the host display sleep and lock, connect from a viewer, and unlock with the password.

1.0.7 sends the host's system sound. The capture stream that carries the picture also captures sound, which is packed as Opus (48 kHz stereo, 20 ms packets) and sent in a new `audio` message. Older viewers close the connection on a message kind they do not know, so the host only offers sound in its display list and sends it after the viewer asks with the `audio` input; sound capture is switched on at that point too. While a viewer listens, the host mutes its default output device and restores it when listening stops, the connection ends, or the app starts again after a crash. The Mac viewer plays through `AVAudioEngine` with a 40 ms cushion and drops sound that falls more than 80 ms behind it, which keeps sound close to the picture without delaying the picture. The Windows viewer uses WebCodecs and Web Audio.

The self test checks the Opus round trip, and the session test checks that sound is sent only after a request, arrives in order, decodes to the test tone and stops on request. `--test-audio-capture <file>` captures the Mac's real sound for a few seconds with the speakers muted; it needs Screen Recording permission, so open the signed app with that argument (`open -n -W "$app" --args --test-audio-capture "$out/audio.txt"`) and read the file. Listening on a real viewer and checking lip sync remain hardware checks.

## Mac input switching in 1.0.22 (build 52)

A Mac host can report two-set Korean while its active keyboard layout is still ABC. The host now asks the frontmost app to switch and checks both the selected input source and the underlying layout. When the input menu protocol is unavailable, it uses the standard input source API. The viewer also clears the Caps Lock modifier from forwarded keys when it consumes Caps Lock for language switching.

To check the fix on two Macs, keep one text field focused. Use Caps Lock on the viewer to type `가`, switch to English and type `rk`, then switch back and type `가` again. The source includes the [macism license](Assets/macism-LICENSE.txt) for the input menu implementation.

## Mac input switching in 1.0.21

The viewer checks its input source before sending a key down so that a detected change reaches the host before the key. The host checks the selected source and retries once after an unsuccessful change. The diagnostics report checks the host’s current selection instead of keeping the previous result.

## Mac viewer in 1.0.15

New installer images contain the Mac viewer under its displayed name, **파이널 퓨전 받기**. DIY update images retain the bundle filename expected by older viewers. Once the old installer finishes, an eligible existing viewer installation changes to the Korean filename and reopens.

Accessibility and Input Monitoring each have a button that opens the corresponding macOS settings. The Input Monitoring row shows green when macOS allows keyboard listening, including through Accessibility.

## Clipboard sharing

The Mac viewer opts in to clipboard sharing. Its host and viewer process clipboard and file I/O separately from screen delivery and connection responses. File transfers run in small bursts. Copied path strings remain text. The self test covers paths, delayed file lookups, and file contents. The session test checks that the host answers a heartbeat during a file transfer. The self test also checks that the same screenshot image is available to paste on both Mac clipboards.

## Connect to the login screen after restart

In 1.0.19, the host’s settings switch checks macOS Screen Sharing, access for the signed-in account, automatic app launch after sign-in, and prior viewer approval. The administrator prompt registers or removes a startup helper. During startup it runs as the host account and relays only a previously approved viewer to macOS Screen Sharing on loopback. The viewer uses the system Screen Sharing window for the host Mac password and reconnects to regular Final Fusion after sign-in.

The startup helper reads separate public app settings. The app compares the bundled executable, installed build number and launch registration and shows **Reinstall startup helper** when a refresh is needed. FileVault disk unlock must happen at the host. The existing relay and ordinary session protocol remain compatible.

The system Screen Sharing client first connects to discover authentication options, then opens a new connection when the password is submitted. The login transport carries both connections over the approved TLS session. Go tests exercise two simultaneous streams and denial of an unapproved viewer. Use a fake viewer to check builds and previews.

Hardware check with the 1.0.19 development build on macOS 27.2.1. The host recognized an older helper and showed the reinstall notice. The settings switch removed and reinstalled the helper. After a real restart, a Mac viewer on a separate internet connection reached the host login screen, signed in through macOS Screen Sharing and automatically resumed the regular Final Fusion session. Video and input delivery were observed on the relayed session. The test used the host’s regular login password with FileVault off.

The public build was checked with local tests. macOS 14–26 hosts, Intel hosts and FileVault-enabled hosts have not been checked on physical hardware.

- Build and signing check passed for the public universal Mac app and helper and the Windows viewer. The public app ID and settings folder were checked, and the installer did not treat the private helper as installed.
- Local simulation passed for self-test, loopback, session, separate transports, fabricated viewer export, and Go tests with and without the race detector. An installer fixture covered setup checks, installation, update detection, failover to the previous helper and removal.
- Public files were checked for private paths, accounts, connection information, credentials and raw device records.

- **AI help and diagnostics:** `AgentSupport.swift`, `Link/ui/*-agent*.txt`.

For sharing, use `"$bin" --support-report-shareable` or copy the in-app AI help. Share only the needed details. The local `--support-report`, `--host-status`, and `--receiver-report` commands may show local paths, relay addresses, or other device details. Do not post their raw output.

Real receiver packages are private: the Mac package contains `Receiver.json`; Windows appends the same kind of data to its executable. Use fake packages for tests and screenshots. Host keys and configuration belong in the user's local application-support folder, never in this repository or an issue.
